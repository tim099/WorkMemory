# 拍板：`op=wrapup`（收工）＋ 晚安的收工閘（Tim 2026-08-24）

## Tim 的要求

「/ucl-task 要加一個收工指令，在這個階段記憶未完工部分；
而**沒觸發過收工的話，晚安流程需要觸發收工**（確保能接回進度）。」

⇒ 它補的是我拍板裡漏的一格：我定了「結單時提示回寫」，
**但沒收工就下線這個洞沒補** —— 而那正是跨多日接回真正會斷的地方
（單子還開著、狀態還是 in_progress，而沒有人知道停在哪一步）。

## ① 一個動作、**兩個目的地** —— 工具負責分流

收工要寫的東西有兩種，而 Tim 先前已經把它們分開過
（「進度由 Task 本身紀錄，記憶不額外記進度」）：

| 寫什麼 | 去哪 | 為什麼 |
|---|---|---|
| **還剩什麼、下一步從哪接** | Task 時間線（`comment`） | 那是**進度**，真相源是 Task |
| **為什麼卡住、試過什麼不行、被否決的選項** | 工作記憶（`pitfall` / `decision`） | 那是**不適合文件化**的部分 |

⛔ **不要讓使用者自己分**。一個 `op=wrapup` 收兩個欄位（`progress` / `why`），
由工具送到兩個地方。
🩸 理由：分流交給人 ＝ 全部倒進同一個地方（今天我自己就把看板快照倒進記憶）。

## ② 誰是寫入端：**記憶那半仍然只有 python 一個寫入者**

契約第①條寫「兩邊各擁有自己那格，不互相寫」。
`op=wrapup` 是 C#，若它直接寫記憶檔就**違反我自己訂的契約**。

⇒ 拍板：**C# 代跑 `work_memory.py`**（FreeTime 的 `op=step` 已有先例），
而不是 C# 自己寫記憶檔。
- 唯一寫入端仍是 python ⇒ 沒有第二套格式、沒有分散式寫入衝突
- 使用者只要一道指令 ⇒ UX 不因為架構而變醜
- ⚠ `why` 的內文**必須由人給**（`--arg-file`），**工具不代筆** ——
  代筆的記憶不是那個人的（同憲法：工具代筆的自介不是妳的）

## ③ 晚安閘：**擋，但跳過要留名**

照既有先例做（`letter-before-sleep` 閘，`c0682c1`）——**不重造第二套閘**。

- 判準：**今天動過**（`updated_at` 是今天）、**未關**、**我是參與者** 的單，
  而今天沒有 wrapup 紀錄 ⇒ 晚安 `step=check` 印出來並**擋住**
- ⇒ 但允許 `--arg skip_reason=<一句>` 顯式跳過，並**寫進那張單的時間線**
  （不是寫進 log —— 跳過要留在別人看得到的地方）

為什麼不硬擋到底：硬擋會在「真的沒東西可寫」時把人關在門外，
而那時他會去找繞過的方法 —— 繞過一次之後那道閘就永久失效了。
📌 **可跳過但留名，比不可跳過更持久。**

## ④ 為什麼收工不等於結單

`resolve` 是「這件事做完了」，`wrapup` 是「我今天不做了」。
兩者混在一起會逼人在還沒做完的時候按結單，或在收工時什麼都不寫。
⇒ 兩個動作、兩個語意；而**只有 `wrapup` 是每天都可能發生的那一個**。
