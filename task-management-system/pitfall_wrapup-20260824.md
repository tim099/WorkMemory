# 收工（2026-08-24，basecamp）—— 為什麼那樣選、踩過什麼

`op=wrapup` 還沒實作（TASK-0019），所以這一筆是**手動照那個設計做的**：
進度寫進 Task 時間線、為什麼寫在這裡。

## 今天我自己造了兩隻同形的（比別人的 bug 更該記）

1. **看板快照放進記憶** ⇒ 跟 `op=kanban` 記同一個量。被 Tim 的「進度不進記憶」照出來。
2. **`related_to` 當主 Task 的傘** ⇒ 一等公民 `subtask_indices` 到位後，
   「子項有哪些」有兩個答案。驗 TASK-0009 時自己撈到，已遷移。

📌 共同形狀：**權宜之計在正式機制到位之後不會自己退場，得有人去搬。**
而兩次都是我**在驗別人的東西時**發現自己的 —— 那個順序值得記：
驗收的副產物是照見自己那一半。

## 三次「讀數過期」（今天講了三遍，形狀完全相同）

- 09:38 我報「現在編不過」—— 那是 09:38 的快照，summit 10:00 就補完了
- 我對她說「claim 現在無條件改狀態，建議先修」—— 她十分鐘前就修了（`270e257`）
- 我引用「`.gitignore` 有 `Plurk/cache/`」—— 寫的當下它沒有

⇒ **指出別人的問題時，那個讀數的時效跟指出自己的問題一樣短。**

## 為什麼記憶側的寫入端只留 python 一個

`op=wrapup` 是 C#，若它直接寫記憶檔，兩個寫入者（Cmd 與 CLI，不同語言不同 process）
就是分散式寫入衝突 —— 而它會在併發時**安靜地覆蓋**。
⇒ 選了「C# 代跑 python」而不是「C# 也能寫」。代價是多一次 process spawn，
換到的是**格式只有一套**。

## 被否決的選項（留著，因為它們看起來都很合理）

- `memory_topic` 用陣列 ⇒ 否決：錨點必須唯一才叫「穩定」；多主題交給記憶側的 `link`
- 久未更新另開一個常數 ⇒ 否決：拍板後兩者量的是同一件事（這張單多久沒動），
  **同一個量就該一個常數**
- QA 閘擴大到 `pm` ⇒ 否決：PM 排序、QA 簽名，混起來會讓「有人管」被讀成「有人驗」
  （而我自己就是那個混起來的人 —— TASK-0009 因此被自動關掉）
- 晚安收工閘硬擋不可跳過 ⇒ 否決：**可跳過但留名，比不可跳過更持久**
