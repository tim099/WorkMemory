# 動這套系統之前要知道的幾件事（2026-08-25，兩天實作下來）

⚠ 這裡**不寫進度也不寫施工順序**（那兩樣在單子上）。只寫「做這幾段要小心什麼」。

## ① 這套系統最常見的 bug 只有一種形狀

**兩個不同的狀態共用同一個輸出。** 兩天下來抓到的幾乎全是它：

- 「讀不到那張單」被算進「不是未關」⇒ 印成「全部關了，可以歸檔」
- `git status` 的空字串有三種來源（真乾淨／被 ignore／問錯 repo）⇒ 守衛只認得第一種
- tracker 有錯 ＋ ErrorLog 也有錯 ⇒ 印「一致（無編譯錯誤）」
- 已歸檔的主題跟 active 主題只差括號裡一個字
- 「沒給這個欄位」與「給了空字串」走同一條路 ⇒ 沒有任何路徑可以清空它

⇒ **改任何輸出之前先問：這一句話底下躺著幾種狀態？**
逐行分得清不代表彙總分得清 —— 彙總是最容易把它們摺在一起的地方。

## ② 驗收的時候，反向對照跟正向一樣重要，而它也會打偏

只驗「它會擋」⇒ **一個什麼都擋的守衛也會通過**。
但反向對照本身也會失手：要對照的是**那一格的相反**，不是「隨便一個不會擋的情況」。
🩸 現場：驗「全關⇒建議歸檔」時先清空成「沒有任何單」——那是第三種形狀，不是對照組。
**而打偏的樣子跟打中一模一樣**（兩次都沒有告警）。

## ③ 「一樣／不一樣」的問題一律用位元組回答

一天內被 grep 的計數騙了五次（ERE 的交替寫成 `\|`／判行尾兩次／`split(":")` 在 Windows／
數字面跳脫序列）。⇒ 檔案比對用 `cmp`／`read_bytes`；行尾用 `count(CRLF)==count(LF)`。

## ④ 這個 repo 的 git 是三層巢狀 submodule

`LY` → `AgentCommands` → `WorkMemory`。
**對父層問子路徑的 status 會回空字串**，而空字串在 porcelain 的語意裡是「乾淨」。
⇒ 任何碰 git 的工具都要先 `rev-parse --show-toplevel` 找出真正擁有那個路徑的工作區；
`HEAD` 也要取那一層的（父層 pointer 長期未 bump，取錯會寫出一顆**指不到內容的 sha**）。

## ⑤ 兩個寫入端記同一個關係 ⇒ 必漂，而且第一天就漂

不要為了「方便查」做第二份索引。能掃出來的就掃，不要存。
🩸 我做過一次（主題卡的 `task_indices` 對 Task 側的 `memory_topic`），
六筆 vs 十四張，第一天就對不上 —— 而它壞掉的樣子跟「沒人維護」一模一樣。

## ⑥ 驗收標準引用現況會過期，而過期不會叫

兩天內出現四次「驗收標準被自己的拍板超車」。
⇒ 寫驗收標準時：**要嘛只寫行為，要嘛附當下的 sha／基準日**。
貼一段 code 片段而不標 sha，等於把一個會過期的東西寫成永久條款。

## ⑦ `op=update --arg criteria=` 是整份覆蓋，而且只給它會靜默 no-op

要擴充驗收細項得 read-modify-write，且必須同時帶一個會計入變更的欄位
（最無害的是 `--arg title="<原標題>"`）。
⚠ 讀原文時**不要用 regex 截「到下一個 `##` 為止」** —— 驗收標準那段裡常有散文小標。
