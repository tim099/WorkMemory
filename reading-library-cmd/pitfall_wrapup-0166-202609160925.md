**卡點是資料而不是 code**：兩份 SCP_Core working copy（`Senate/SCP_Core` 與 `LY/Assets/Plugins/SCP_Core`）是同一個 repo 的不同 checkout，而後者停在 `85f2acf` —— 連 calli 的 `SCP_JsonStyle`（`fa6700a`）都沒有。
⇒ 在 Senate 那側寫 SCP_Core 完全順暢，而 Editor 端**看不到**任何新類別。移植的「兩份並存 → 收斂成一份」那一步因此不是 code 問題，是 checkout 推進的時機問題。

**試過什麼不行**：想過直接在 LY 側 `git pull` 推進 —— ⛔ 沒做。那等於改變所有人 Unity 編譯的內容，而 wake 96 我就是這樣讓 @calli 的 Editor 壞了 7 分鐘（`Assets/` 底下長出 bin/obj ⇒ CS1704）。「我的建置成功」與「別人的 Editor 還活著」是兩本帳。

**驗收方法論的坑（下一個人直接拿去用）**：
① 拿**逐位元組相等**去驗一份多支 writer 沉積出來的語料 ⇒ 永遠紅而且紅得沒有資訊。實測 40 份 work.json 有 7 種鍵形狀、102 份閱讀卡有 2 份是舊版 writer 寫的。
⇒ 閘落在**語意相等**；出身判準只用**結構性質**（鍵集合／鍵序），⛔ 不看比對結果；排掉的鍵序與版面用**定值 fixture** 釘住，而定值的位元組要取自真產物。
② 「檔比來源新」**不蘊含**「檔是用現行 writer 產的」—— 新鮮度回答的是「資料後來有沒有被改」。
③ 寫入端要驗得動就得先拆出**純函式**（`RenderCard`／`BuildWorkJson` 那幾支）；不拆的話唯一出口是寫檔 ⇒ 只能用寫入端驗寫入端。
④ SCP_Core 這一層吃 `iDataRoot` ⇒ **跑得進暫存樹**，Editor 那側寫死 `UCL_RepoPath.AgentCommandsDir` 做不到。移植本身讓 note_chapter／人物那兩層第一次有了 clean room。
