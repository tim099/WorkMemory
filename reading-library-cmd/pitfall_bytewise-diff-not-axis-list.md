**「逐位元組對拍」不要靠軸表，靠對拍本身 —— 軸表永遠是不完整的，而它不完整的時候長得像完整的。**

換寫入端（python → C#、UCL → SCP）時，判定「搬對了」的唯一可信方法是同輸入兩邊輸出**逐位元組**比。
⚠ 而「列出格式有哪幾根軸」這件事**本身會漏**，且漏掉的軸不會讓任何讀數變紅。

## 🩸 血證：同一天，同一個人，軸表漏了兩次（2026-09-11 calli，TASK-0200／TASK-0166）

| 第幾次 | 我當時的軸表 | 漏掉的 | 抓到它的是什麼 |
|---|---|---|---|
| 09-10 | 行尾 | 縮排、冒號空格 | 隔天重量磁碟 |
| 09-11 上午 | 行尾 ＋ 縮排 ＋ 冒號空格（＋結尾換行） | **陣列括號位置**、**空容器渲染** | ⭐ **`git diff -w` 這個反向對照**，不是我那把尺 |

第二次漏掉的兩根：UCL 的 `ToJsonBeautify` 把 `"aliases":` 與 `[` 拆兩行、空陣列寫成
「`[`、空行、`]`」；`SCP_JsonWriter` 寫 `"aliases": [` 與 `[]`。
⇒ 兩者 `json.loads` **逐鍵相等**，而位元組差 29 B／檔。

📌 而我那把三軸尺**量不到它們**，因為它只讀第 2 行。
⇒ 一把「只看得到自己列出的那幾根軸」的尺，在漏軸時的輸出跟「完全相同」一模一樣。

## 動作型判準

1. **驗收用逐位元組比，⛔ 不用軸表比。** 位元組相同涵蓋所有軸（含還沒被命名的）。
   軸表只配拿來**描述現況**與**分類磁碟存量**，不配當通過條件。
2. **每次都加一行反向對照，而它要用跟主尺不同源的工具。** 這次救場的是 `git diff -w`
   ——它的射程跟我的 python 軸偵測不重疊，所以它看得到我看不到的。
3. **描述軸的段落要顯式標「已知軸」而不是「軸」。** 寫「三根軸」的那一刻就是在宣稱完整。
4. 移植寫入端前先確認新 writer **零呼叫端** —— 零呼叫端時修是改一個參數，有呼叫端之後是改參數＋救資料。
5. 序列化器沒有參數可關的那幾根軸（冒號空格／括號位置／空容器）＝**改 writer 或走同一支 writer**，
   ⛔ 不要在呼叫端做字串後處理（那會把「格式」散到每個呼叫端，而下一個呼叫端不會知道要做）。

## 落地形狀（TASK-0200 的解法，可複用）

⛔ 不要教第二個 formatter「學會」第一個的格式 —— 兩份 formatter 保持同步靠的是記得注意。
✅ 把型別邊界收成一個點、走同一支 writer：`JsonData → 文字 → SCP_JsonData → SCP_JsonWriter`
（先例：`UCL_PersonaProfile:137` 的反向，那裡寫著「收成一個點的理由是**它可驗**」）。
⇒ 格式漂移從此在結構上不可能，而不是靠下一個人記得。實測：兩個寫入端同輸入 **316 B 逐位元組相同**。
