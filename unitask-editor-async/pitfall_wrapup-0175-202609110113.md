既有的 offload 三問②寫著「grep PlayerPrefs / EditorPrefs / AssetDatabase… 掃主緒 only 的 API」。
今天 TASK-0175 量出那一問**不夠**，而不夠的方式有兩層，兩層都不會出聲：

① **命中了也可能不炸，而沒炸不等於沒有。** `Cmd_Tavern.Op_Read` 三處 settings 呼叫全寫在
   三元的「參數沒給才求值」那一側（`limit > 0 ? limit : Settings.X`）⇒ C# 短路 ⇒
   **帶了參數的呼叫端永遠不會執行那一行。** 於是 grep 命中 3 處、日常零症狀，
   而第一次照文件打裸指令的人 100% 炸。
   ⇒ 掃完要再問一句：**這幾處在「哪一種呼叫」上會被求值？** 答案通常是「參數最少的那一次」。

② **真正的觸發條件是環境狀態，不在 code 裡。** `UCL_ChatTavernSettings.Get()` 的序是
   JSON → legacy `PlayerPrefs` → 預設值 ⇒ **只有 JSON 缺那一欄時才會碰主緒 API。**
   陰性對照（把 `since_limit` 寫成它自己的預設值 200 ⇒ 行為零變化）：那條立刻 Success，
   檔刪回去立刻 Failed。⇒ 任何人開過後台設定頁按過儲存，bug 對所有人同時消失；
   換機器／新 clone 對所有人同時出現。**「在我的機器上是好的」的製造機。**
   ⇒ 於是同機複驗在這一族上特別沒有力量 —— 十次讀數共用同一個環境狀態。

③ 前瞻一格（便宜到只花一次 grep）：`Cmd_Tavern.cs:1015` 的 `LastViewTailCount` 在 `Op_Post` 的
   **無條件**路徑上（每則 post 都寫 `_last_view.md`，沒有參數能短路）。post 今天沒 offload 所以安全，
   而 TASK-0164 就是要 offload 它 ⇒ **那一天不是「少給參數才炸」，是 100% 的 post 全炸。**
   ⇒ 掃的時候要把「這支還沒 offload」的檔案也看一眼：**下一個 offload 的人會繼承它，而他不會重掃。**
